Read this before you file anything

These are deliberate sandbox behaviours, not defects. Filing them costs triage time.

  • No real money. Every payment is a sandbox capture. "Pay online" succeeds without a card.
  • No real SMS, WhatsApp or push. OTPs are displayed on screen in the app; staff notifications land in the in-app alert queues.
  • Video slots are empty on purpose. Every service banner has a slot labelled as awaiting real footage.
  • Just after a deploy (we announce them) the first minute can serve a mix of old and new versions. Retry once before filing.
  • "Slot taken" or "no schedule available" with several testers on one date is usually the roster genuinely being full — there are only 2–4 seeded providers per service. Spread your test dates across the next 2–3 weeks.
  • An empty screen that explains itself is passing. "Nothing recorded yet", "open with a canonical booking ID" and "not yet linked to a provider" are the product doing its job on a fresh database.

The AI assistant, before you judge it

The assistant is deliberately fail-closed: it answers nobody until four separate conditions are met, so "the AI does nothing" is the expected state rather than a bug. Start at /team/ai/configuration — the panel at the top ticks or crosses each condition and says what to do about it.

  1. A model provider is connected (a PAWSPACE_AI_PROVIDER_API_KEY secret). Not set on staging by default.
  2. Assistant grounding is activated — press Install starter assistant grounding if it is missing.
  3. The rollout audience is widened on /team/ai/rollout: off → staff_only → customers.
  4. No kill switch is thrown — the Disable and Enable AI buttons on that same screen.

With the demo seed loaded, gate 2 is already done and gate 3 sits at staff_only, so these screens carry real data:

  • /team/ai/analytics — 7 governed turns across WhatsApp, chat and voice, with a containment rate, latency, token and cost totals, and 2 explicit CSAT ratings. Conversion and first-response deliberately read "not claimed" and "not attributable yet"; that is a design decision, not a gap.
  • /team/ai/handoff — pick a canonical thread. UATD-TH-1 is a customer asking for a human and being taken over by staff. UATD-TH-3 is a refund dispute the policy rules blocked and routed to the finance CX queue — the assistant is not permitted to answer it at all.
  • /team/ai — the safety contract result and the human review queue for AI suggestions.
  • /chat — Public mode answers only from the approved knowledge base. Authenticated mode needs a canonical customer ID (UATD-CUS-1) and uses that customer's own record.
Every seeded AI reply is scripted. They are recorded on the turn as uat_demo_scripted — none of it is output from a live model.

Running it locally

Node >=22.13.0, and Linux is recommended — the bounded install and build helpers use flock and GNU timeout.

git clone https://github.com/PawSpaceIND/pawspace-tech-platform
cd pawspace-tech-platform
npm ci
npm run dev        # Vite/vinext dev server

npm run lint       # eslint
npm run typecheck  # tsc --noEmit

Run the screen sweep before clicking anything

This opens every route in a real browser, waits for the client fetches to land, and reports which screens a tester can actually use.

npm run dev &
npm run sweep                                 # all 130 routes
npm run sweep -- --only=/team                 # one subtree
npm run sweep -- --json=sweep.json            # machine-readable; diff two runs
npm run sweep -- --base=https://<staging-host> --cookie="<session cookie>"

Most staff screens are client components: the server sends a shell and the numbers arrive from fetch() after hydration. Every blank screen reported from staging so far had that shape — a page whose cards sat inside {data && ...} and never rendered. curl sees a 200 and calls it fine. Only a browser that waits for the fetches can see an empty page.

LevelMeaning
OKRendered real content, or said honestly why it had none
BLANKAlmost no text, nothing to interact with, and no explanation
THINA header and little else, with no empty state and no input — a tester cannot proceed
DATAAn API the page calls failed in a way the platform does not do by design
BROKENDid not load, 5xx, or an uncaught error
MISSING404
NOT TESTEDThe route correctly refused an anonymous call, so the sweep never saw the real screen — re-run with --cookie

NOT TESTED is not a pass. Roughly a dozen customer and partner routes need a real session, and the sweep says so rather than scoring them green. Check the excerpt the sweep captured before filing — each finding carries what the page actually said.

Do not read the test suite as verification. The ~690 tests in tests/*.test.mjs are static regex checks against source text. They are genuinely useful for catching accidental copy and markup regressions, but they do not execute application code — they will not catch a runtime bug, a missing database table, a dead button or bad business logic. A green suite is not evidence that a flow works. Real verification in this repo means a script that calls the production functions against a real database, or the browser sweep above.

Where things live

  • app/ — all web routes and API routes. Customer journeys, plus app/partner/, app/team/ and app/control/ for the three staff experiences.
  • lib/ — the booking engine, pricing and offer engines, auth/RBAC helpers and fixture data.
  • db/ and drizzle/ — D1 schema and the ordered migration history.
  • backend/ — the standalone Fastify platform API, with its own npm ci.
  • docs/ — per-module UAT specs and closure plans, if you need the detail behind a flow.
  • HANDOFF.md — what has actually been verified by real execution, and what has not.

Staging is isolated from production: its own Worker, its own D1 database, sandbox posture throughout. Nothing you do here can reach live customers, live providers or live money.
