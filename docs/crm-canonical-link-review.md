# Disabled staff-reviewed canonical enquiry linking

`POST /api/crm/intake/link` links a previously staged immutable enquiry to an existing canonical customer and matching open lead. It does not create the customer/lead, invoke scheduling, send communications, assign providers, create bookings/payments or call external providers.

Both `CRM_PLATFORM_INTAKE_ENABLED` and `CRM_PLATFORM_CANONICAL_LINK_ENABLED` must equal the literal string `true`; absent or false returns 503. No deployment configuration enables either flag in this change. Existing `customers.manage` authorization, active staff identity, role/MFA policy and CRM manager domain remain authoritative. The exact gateway path maps to `customers.manage`, with no public/prefix exception or new grant. Declared direct Workers ingress cannot authenticate with spoofed workspace headers or an operator Bearer token.

Body is bounded to 64 KiB and allows only `inquiryKey`, `customerId`, `leadId`. The request cannot claim reviewed status, account/city scope, role, auth or scheduling evidence. Server policy names `CRM_PLATFORM_INTAKE_EXOTEL_ACCOUNT` and `CRM_PLATFORM_INTAKE_CITY_ID` must explicitly match the staged source/account and canonical city; provisioned managers must also match their existing CRM city/team/department. The handler checks an immutable receipt, real canonical ownership/service/lifecycle via `validateBookingOrigin`, unique phone identity and the reviewed canonical-link helper. Identity, scope, lead state and receipt presence are rechecked in conditional SQL. Replay retains one linkage and its first timestamp. A returned handoff is not a slot reservation or booking confirmation.

`migrations/0001_crm_intake_bridge.sql` is an additive, unapplied candidate copied from the prior disabled bridge proposal and hardened to make all event identity/account/inquiry/fingerprint/envelope/time fields immutable. Exact no-op UPDATE/ingestion replay remains allowed. Review numbering/ledger and core tables against the target before applying. This file is not added to deployment/migration execution. If an older bridge migration was already applied, its owner must supply a reviewed forward migration replacing the receipt trigger; do not silently rewrite applied history. `lib/crm-intake-bridge.mjs` reuses existing platform phone/service normalizers; no new canonical store/model is introduced. The upstream `/api/crm/intake` staging route is not installed by this PR: a staged immutable event is a required dependency.

`lib/crm-scheduling-readiness.ts` is pure preparation for existing `UatScheduleRequest`. Its trusted server-derived identity/auth/address/pets/request/availability/calendar/travel evidence must match and be fresh; missing/ambiguous data, overlap, conflicting replay and stale/missing road evidence explicitly hold. It emits preview only, never reserve. Scope is a single grooming/training/walking appointment; specialized stay/taxi and recurring workflows hold. It is not wired to any live caller. A caller-supplied boolean is not evidence or authentication.

Bounded future road-ETA integration: reuse `computeGoogleRoute` after existing roster/capacity/radius/fixed-buffer filtering; at most three candidates/two adjacent route legs each, concurrency two, overall ten-second deadline, no retries, exact provider/location/window/calendar revision cache up to60 seconds. Unavailable/malformed/missing routes hold; no haversine ETA fallback. Propagate the deadline/AbortSignal into the existing adapter before wiring; revalidate calendar and selected candidate before existing atomic commit. This integration is designed, not implemented or enabled here.
