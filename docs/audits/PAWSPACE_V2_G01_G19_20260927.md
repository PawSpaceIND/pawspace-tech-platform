## Implemented and locally verified

**G10, pre-reservation navigation:** four real buttons for Pets, Package, Address, and Time & review. Keyboard activation moves focus to the labelled section. Navigation neither resets the draft nor calls an API; mandatory pet/package/address checks and the reservation lock still apply. Address changes invalidate affected availability and checkout readiness. The existing booking-ID payment/recovery flow is unchanged; this does not implement editing an already-created booking from the pre-reservation form.

**G03, UI selection gap:** preselect the first groomer from the server's verified, ranked, read-only shortlist, including when several are available. The customer can change that selection. Empty or unverified lists cannot enable checkout. This is reuse of the existing scheduling engine, not a new AI model or completed preferred-groomer/history integration. Reservation still revalidates the provider and refuses a changed selection.

**G08, stale coupon result:** invalidate an unmounted coupon form's request version. A late success or refusal for an old package/date/price cannot overwrite the new basket's coupon. Coupon amounts, quote revalidation and redemption authority remain server-controlled.

**Mobile clipping:** the date strip could make the form 1,495px wide inside a 412px viewport while page-level hidden overflow concealed the error. Constrain the booking fieldset and sections to their column. A browser regression now checks actual section edges, not only document scroll width. The final mobile form is 356px wide and entirely inside the viewport; the date strip retains its own horizontal scrolling.

## Verification and release boundary

Final local results: **371/371** targeted unit, integration and presentation-contract tests; **30/30** Chromium desktop/mobile browser scenarios; `npm run typecheck`, targeted ESLint, `npm run build`, and `git diff --check` pass. These are targeted checks, not the repository's complete test suite.

The browser suite executes the actual built V2 UI with explicitly controlled API and Razorpay SDK fixtures. It does not place a real booking, execute a real sandbox gateway transaction, or prove deployed staging behavior. Original payment-confirmation, duplicate-click, address recovery, ownership rejection and payment-return scenarios remain and pass. Four new scenarios run on both viewport projects: draft-preserving navigation with visible bounds, multi-provider preselection, stale coupon success, and stale coupon refusal.

A first browser run was interrupted by a Mac restart; its retained failure trace was a page-bootstrap timeout before address assertions. A clean rerun passed unchanged. Visual review then exposed the real mobile clipping issue, reproduced with an added failing boundary assertion and fixed before the final 30/30 run.

Presentation baseline updates are restricted to hashes for the intentionally changed grooming page, stylesheet, and extended browser test in existing manifests. No unrelated hash, authorization assertion, payment invariant, test skip, or production flag was relaxed. The approved stylesheet's original pre-theme bytes are unchanged.

This branch does not modify the separate session/logout or Founder-access fixes. It does not merge, deploy, or change a live payment/AI/provider policy. Keep the PR draft until repository CI, review, and integration with parallel UI work are complete.
